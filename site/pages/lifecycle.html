The project follows a tailored, incremental V-model, as planned in the software development plan. Each increment carries one capability down the left side of the V (requirements, design, code) and back up the right side (unit, integration and system verification). Verification is therefore planned against requirements from the start, not invented after the code.

The FDIR increment was added alongside the baseline, not by editing it. The baseline requirements stayed frozen, and the ones the increment affected (cycle timing, the command set) were re-verified rather than assumed to still hold.

Controls that kept it traceable

  • Verification method fixed when the requirement is written. Test, Analysis, Inspection or Review is chosen with the requirement and never changed by later evidence. A requirement assigned Review stays closed by Review, even when tests were added on top.
  • Every baseline is an annotated git tag. Any reviewed state can be checked out and rebuilt.
  • Every change is reviewed by pull request. Each phase was a pull request (PRs #1 to #8) reviewed before merge, with findings dispositioned in the PR.
  • Commits name requirements. A commit that satisfies or changes a requirement carries its ID.
  • Documents are versioned like code. Requirements, design and verification records are Markdown in the repository, so they diff and review like code.
  • CI on every push. Build with warnings as errors, 66 unit tests, cppcheck, and a MISRA C:2012 gate that fails on any Mandatory or Required finding.

Traceability

The traceability matrix is the spine of the evidence. From any requirement, one row gives the verification method, the design element, the code, the verification evidence, the ISVV item and the status. Each module and public function also names, in a comment, the requirement IDs it implements, so the trace runs from code back to requirement without leaving the file.
