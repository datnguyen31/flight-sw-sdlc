What verification found

System verification raised four findings. They are listed because finding things is the purpose of verification, and each one changed the project.

IDFindingOutcome
SYS-1A malformed uplink frame was rejected silently, so the rejection could not be observedFixed. ST-04 verifies it
SYS-2ST-10 as specified could not detect an off-by-one in the debounce count N. A mutant with N = 2 passed itFixed. The test now also runs N − 1 samples, and the mutant fails
SYS-3Safe-mode state is not in telemetry, so ground cannot see that a clear took effectOpen. Requirements decision needed (OI-4)
SYS-4The output path cost 2 to 4 times its analysis boundClosed by timing analysis revision 3

Two findings worth reading in full

The tests were tested (SYS-2). All ten system tests passed first time, which is not evidence that they would catch a defect. So the checker was attacked: five deliberately tampered logs and one code mutant. The mutant changed the debounce count from 3 to 2 and still passed the specified ST-10, which only tried a single out-of-limit sample. The specification was extended with an N − 1 run, and the mutant now fails.

Measurement corrected the analysis (SYS-4). The analysis said a collection cycle costs 0.99 ms. Measurement gave 0.57 ms, so the total agreed with a wide margin. The split did not agree: the console sink cost far more than the analysis assumed for a queue handoff, and the computation far less. Revision 3 bounds the sink per implementation, and shows that this console stand-in on a real 115200-baud UART would cost about 26 ms per packet. That is why it must not be the flight sink.

MISRA C:2012 conformance

The coding standard names the MISRA C:2012 Mandatory and Required rules as its basis. A first run of cppcheck's MISRA addon found six Required findings, with no deviations logged. All six were corrected in code, with no change in behaviour:

RuleWhereCorrection
12.2 × 2Encoder header flag constantsWritten as the 16-bit literals 0x0800u and 0xC000u
10.8 × 2Encoder packet error controlPointer differences held in ptrdiff_t before the cast
8.4Init entry pointPrototype placed before the definition
21.8End of the scripted runrtems_shutdown_executive(0) instead of exit()

A MISRA gate now runs in CI on every push and fails on any Mandatory or Required finding, or on an addon that did not run. HKS-SR-170 stays Partial for an honest reason: cppcheck's addon covers only part of the MISRA rule set, and clang-tidy is not yet run. A clean gate shows that no checked rule is violated. It is not a full conformance claim.

Verification asks whether the service meets its requirements. Validation asks whether those were the right requirements. The yardstick is the four mission needs, written from the mission side.

SYS-030: telemetry is placed on the mission timelineEvery report carries the CUC time of its collection. Events carry the time of the report that confirmed themYes
SYS-040: autonomous response to out-of-limit healthConfirmed conditions reported by severity, transients ignored, critical condition holds safe mode until ground clears itYes, with a gap (OI-4)

What validation found that verification did not

Every requirement under SYS-040 passes. But an operator who sends CLEAR_SAFE_MODE gets "accepted" back and nothing in telemetry showing that safe mode was left. The requirement does not ask for it, so verification could not catch it. It took asking what the operator needs. It is carried as an open item with a recommended new requirement, an informative "safe mode exited" event, not patched quietly under the existing one.

The developer did the validation, against written mission needs, with the mentor as review authority. No operator or ground-segment user took part. On a real project that is the first thing to add.
