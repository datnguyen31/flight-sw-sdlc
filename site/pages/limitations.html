A verification result is only as useful as its stated boundary. This page lists what the project does not claim, the open items with their closure actions, and what would still be required before the software could be called flight-ready. It is the short answer to "what is this not?"

This is not flight software

It is a flight-representative capstone: one onboard function, run on an emulated target, verified against requirements written for this project. The verdict "verified" applies to that scope only.

What is representative, not real

  • Parameters and limits. The 32-parameter set, the limit values (raw 12-bit counts) and the parameter providers are training values. The target's provider is a simulator.
  • Telemetry sink. The target sink is a console stand-in. It is not a flight sink: on a real UART it would cost about 26 ms per housekeeping packet.
  • Safe mode. It sets an indicator and reports it. Safing actions such as load shedding and attitude changes are system-level behaviour beyond this unit. The code marks the hook.
  • Emulated timing. Renode models no caches, wait states or bus contention, and its UART transmits instantly. Emulated time is deterministic, so a jitter of 0 µs says nothing about interrupt latency on a real LEON3.
  • BSP. The standard RTEMS leon3 BSP, with two boot-loader duties done by the Renode script. It is not a mission BSP.
  • Validation. Done by the developer against written needs. No operator or ground-segment user took part.

Next increments

The design was built to accept further capability without rework: configurable report definitions (PUS Service 3 create, enable and disable per structure ID, deferred by DD-05), a real downlink sink behind the existing interface, a deeper FDIR hierarchy, and a mission BSP on real hardware. Each would attach as new requirements and be verified the same way.
