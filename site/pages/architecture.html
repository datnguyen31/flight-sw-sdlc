Six baseline components sit behind two designed interfaces, the parameter source and the telemetry sink. The FDIR increment adds four components in their own directory and attaches to the pipeline at one point: after a report is built and before the reporting gate, so FDIR checks every sample whether or not reporting is enabled.

RTEMS task structure

The service runs as two tasks with statically defined priorities, stacks and queues (HKS-SR-180). All RTEMS objects are created from static storage at startup, and nothing is allocated after it (HKS-SR-160).

TaskRTEMS priorityActivationRole
Command task10 (higher)Event: blocks on a message queue, depth 4Receives a telecommand, validates it and dispatches it. No blocking work, so a command never waits behind a collection cycle
Collection task20Periodic: rate-monotonic period, 1000 msRuns hk_collection_step() each release. Every fourth release that finds reporting enabled emits a report

The two tasks share two flags: reporting enabled, and safe mode. Each has one owner, and both are guarded by a priority-inheritance semaphore, so a low-priority holder cannot be preempted indefinitely by work in between (DD-07, DD-11). Each task is a thin loop around a logic call, and all logic is plain C11 with no RTOS calls, so it is unit-tested on the host through the same interfaces the target uses.

Key design decisions

Each decision is recorded with its reason and the alternative it rejected, in the design decision log (DD-01 to DD-18). The ones that shaped the design most:

IDDecisionWhy
DD-01One periodic task with a report divider, not two tasksEach report aligns with a completed collection by construction, and there is one timing source to reason about
DD-02Static allocation onlyMakes "no dynamic memory" something an inspection can prove
DD-03Swappable implementations behind pure C interfaces, chosen at link timeThe same logic links against stubs on the host and real providers on the target. No function pointers
DD-04Reporting disabled at startA quiet start is safer and easier to verify than autonomous output
DD-07The command handler asks the manager; it never writes the flagOne owner for the one piece of shared state
DD-12FDIR events on their own APID, stamped with the confirming report's timeThe verified housekeeping stream stays unchanged, and an event lines up with its data on the ground
DD-13A confirmed level per parameter, raised by saturating counters, acting only on a riseA sustained condition is reported once, and a warning can escalate to critical
DD-18Renode, not QEMU, as the LEON3 emulatorReproducible virtual time, scriptable boot state and hooks, platform described as text (see below)

Target and emulator

The target is RTEMS 7 with the standard sparc/leon3 BSP, run on Renode's LEON3 platform. Renode starts the processor raw, so the launch script performs the two duties a boot loader would: it sets the initial stack pointer at the top of RAM, without which the BSP halts before any console output, and it programs the GPTIMER prescaler, without which time runs five times slow.

Why Renode and not QEMU. QEMU's leon3_generic machine models the same core and was the obvious alternative. Renode was chosen for what the verification needed:

  • Reproducible time. Virtual time advances by executed instructions, so the same image gives the same timestamps and sequence counts every run. System tests re-run on 2026-10-29 and 2026-11-03 reproduced the 2026-10-16 recorded run exactly.
  • Scriptable state and hooks. A hook on malloc is the run-time evidence that nothing allocates after startup, and hooks on the BSP fatal handler located the silent boot fault.
  • Platform as data. The machine is a text description, so a peripheral, such as a second UART for a real downlink sink, is added without writing emulator code.

Neither emulator models caches, wait states or bus contention, so timing from either is indicative only. Nothing in the flight code depends on Renode: everything emulator-specific lives in tools/renode/. QEMU was not run on this image.
