# Design Decisions

| ID | Decision and Rationale |
|---|---|
| DD-01 | A single periodic collection task with a report divider, rather than two independent tasks. One rate-monotonic period drives collection; a counter decides when a report is emitted. This guarantees each report aligns to a completed collection cycle (HKS-SR-060) and keeps timing reasoning simple. |
| DD-02 | Static allocation only. All buffers, including the report buffer, are sized at build time. No allocation after initialization (HKS-SR-160), avoiding fragmentation and non-deterministic timing. |
| DD-03 | Parameter access and telemetry output go through pure C interfaces with swappable implementations. Real providers and a real downlink in flight, stubs in unit test (HKS-SR-030, HKS-SR-090). Testability is designed in, not retrofitted. |
| DD-04 | Reporting state is a single flag, disabled at init. Enable and disable commands set it; the report step consults it (HKS-SR-100, 110, 120). A quiet start is easier to verify than autonomous output. |
| DD-05 | Fixed APID and fixed structure identifier for the baseline. Configurable report definitions are deferred to a later increment, keeping the first structure simple (HKS-SR-050). |
| DD-06 | Target RTOS: **RTEMS**, using its rate-monotonic period service for the collection task. Chosen for consistency with prior RTEMS background and alignment with the QEMU emulation environment set up in Session 2. Architecture, interfaces, and data model are RTOS-agnostic; only the task/timing primitives are RTEMS-specific. |
| DD-07 | `hk_manager.h` gains `hk_manager_set_reports_enabled()` alongside the existing `hk_manager_reports_enabled()` getter. Session 4 defined how the Scheduler reads reporting state but not how the Command Handler writes it; the detailed design (Session 5) needs an explicit mutator, called only from the command task under the critical section in `design/detailed-design.md` §1.6. |
| DD-08 | RTEMS BSP pinned to **arm/beagleboneblack**, the only BSP built in the `/opt/rtems6` toolchain install; cross-compilation is wired up via `cmake/toolchain-rtems-beagleboneblack.cmake`, verified by building `src/app/rtems` (a smoke target, not the HK-TM application). This BSP boots on real hardware over TFTP, not under QEMU — the BSPs QEMU can emulate (e.g. `realview_pbx_a9_qemu`) are not built in this install. Running the cross-built image is deferred to real hardware or a later QEMU-capable BSP; until then, verification of RTEMS-hosted behaviour stays by analysis/inspection rather than by an emulated test run. |
| DD-09 | Emulated target for Session 7 onward: **RTEMS 7, BSP sparc/leon3, run under Renode** (LEON3 platform), installed at `/opt/rtems7`; cross-compilation via the generic `cmake/toolchain-rtems.cmake` (BSP selectable; the DD-08 beagleboneblack file is now a preset of it). This lifts DD-08's deferral: RTEMS-hosted behaviour is now verified by an emulated test run. sparc/erc32 was built first, but neither QEMU nor Renode models ERC32 (QEMU emulates only `leon3_generic` for this family; Renode models LEON3, not ERC32's MEC). LEON3 shares the SPARC V8 CPU, compiler and RTEMS API with ERC32, so the application is unchanged across the two; the same image also builds for erc32 and runs under SIS, the ERC32 reference simulator. Renode starts the processor raw, so `tools/renode/hk_leon3.resc` performs the two boot-loader duties RTEMS's leon3 BSP expects of GRMON/mkprom: initial `%sp` at the top of RAM (RTEMS sizes its work area from it; left at 0 the first allocation fails and the BSP halts with `LEON3_FATAL_NO_IRQMP_CONTROLLER`), and a GPTIMER prescaler giving 1 MHz (left at Renode's reset value, every clock tick runs ~5x slow). |
| DD-10 | The per-release pipeline of the collection task (detailed-design.md §1.1) is a pure C module, `hk_collection.c`, with the RTEMS task (`tasks/hk_collection_task.c`) reduced to the rate-monotonic loop and the time source. This moves the report divider (HKS-SR-060), the enable gate, and the sink hand-off (HKS-SR-090) from target-only code into the host-tested library, so they are verified by unit test rather than only by an emulated run. |
| DD-11 | Critical-section primitive (detailed-design.md §1.6): a binary semaphore with **priority inheritance**, `hk_critical_rtems.c`, chosen over an interrupt lock because the command task (higher priority) and collection task (lower) contend for it and inheritance bounds the inversion. This adds `hk_critical_init()` to `hk_critical.h`, called once by Init before `hk_manager_init()` and before either task starts. A failed semaphore directive is escalated to `rtems_fatal()`: an unusable mutex leaves the flag unprotected, and a fatal error is the defined safe response (coding-standard.md rules 5, 7). |
